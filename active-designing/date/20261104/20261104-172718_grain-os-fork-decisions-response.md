This responds to Keaton's twelve-point message following the Hammock-Driven architecture comparison of grain-os (`gratitude/grain-os/`) against our tree. Each section addresses one of his points, with the detail he asked for on Q4 through Q11.

## Q1. RV32I -- acknowledged

Keaton confirmed: our tree targets **rv32i**, the minimal 32-bit integer-only RISC-V base. grain-os targets rv64; the two make different trade-offs. Our choice follows the TAME width discipline -- `u32` in-memory, `u64` wire -- and the principle that a bound placed at the smallest honest machine keeps the software honest about what it allocates. A 32-bit address space is 4 GiB, which is more than a small farm's personal server needs and less than what lets a program hide an unbounded allocation behind a large address space.

The order Keaton named -- "following the order we decided was most TAME-aligned" -- means rv32i lands as part of the Terrarium boot journey (`tablecloth/20261103-184811_glow-language-journey/`), where the first pill boots a minimal Caravan on rv32i under emulation.

## Q2. Rye -- acknowledged

Keaton confirmed: our language is **Rye**, with Glow above it and Rishi beside it. grain-os is pure Zig. The composition seam sits at the boundary -- grain-os's Zig kernel core stays Zig (inherited std, per `context/specs/inherited-names.md`), while our modules above the kernel are authored in Rye. The `@import` boundary between the two is where a future interop shim would live, the same way `tally/copy.rye` wraps `@memcpy` at the seam today.

## Q3. ZON, `*.{name}.md`, Ember voices, 100-char ratchet, code block wrapping, molt breach

This is the largest point. Keaton's vision touches six subjects, and each deserves its own section.

### ZON -- two different things sharing an acronym

**zonformat.org** and **Zig's ZON** are completely different projects that happen to share an acronym:

- **zonformat.org** ("Zero Overhead Notation") is a data format by Roni Bhakta, MIT-licensed, with Python and TypeScript libraries. It is designed to use roughly 50% fewer tokens than JSON when fed to LLMs -- a serialization format optimized for AI context windows. It has its own syntax (no quotes on keys, no commas, indentation-sensitive).

- **Zig's ZON** ("Zig Object Notation") is a subset of Zig syntax, built into `std.zon` (`std.zon.parse`, `std.zon.stringify`). It is what `build.zig.zon` files are written in. grain-os's Brix evaluates to Zig's ZON -- the manifest language produces typed Zig data.

These are not the same thing, there is no single-stranded sameness between them, and the coincidental name collision is worth recording so it is not re-derived later.

**Our parallel to Zig's ZON is Kyri notation** (`.kyri`, `.kyri.md`). Kyri is plain key-value text, one field per line, `#` comments, no quotes, no braces -- valid Markdown by construction. Where grain-os's Brix evaluates to Zig's ZON, our Brix would evaluate to Kyri. The relationship is:

| grain-os | Our tree |
|---|---|
| Brix (manifest language) | Brix (composition language, `.brix.md`) |
| evaluates to Zig's ZON | evaluates to Kyri |
| `std.zon.parse` reads it | Scribe reads it |

zonformat.org is a third thing entirely -- an LLM-oriented serialization format. It could be studied as a gratitude project if its token-efficiency claims prove useful for Ember voice or Comlink wire formats, yet it is not a replacement for either Zig's ZON or our Kyri.

### The `*.{name}.md` format

Keaton's vision: our compressed receipts and plain data formats use `*.{name}.md`, where the name carries the format identity. Brix files become `*.brix.md`. This is already the direction the session log molt took on `20261020` -- `.kyri` became `.kyri.md` so GitHub renders logs with live Markdown hyperlinks.

The extension family would be:

| Format | Extension | What it holds |
|---|---|---|
| Kyri notation | `*.kyri.md` | Session logs, standing equipment, fleet roster, plain data |
| Brix composition | `*.brix.md` | System manifests, module declarations, config |
| Mycelium network | `*.myc.md` | Network topology, peer declarations |

Each is valid Markdown by construction, so GitHub renders it. Each carries its format identity in the extension, so tools know what parser to reach for. The `.md` suffix is a rendering hint rather than a format claim -- the format is the `*.{name}` part.

### Ember voice system -- session logs generated by Brix template

Keaton's vision is precise and clean: the session Ember voice is a **config parameter** rather than a code path. A Brix template generates logs, and the voice is set once in config:

```
# in root or tablecloth-level Brix config
ember_voice = kyri
```

Then logs are written as `*.{ember-voice-choice}.md` -- today that is `*.kyri.md`, and if the voice were changed to (say) a future name, only the config line changes, not the implementation code of the compressed receipt and plain data format.

One-off voice choices are a flag: a prompt that wants a different voice passes it, and the log carries that voice in its metadata without changing the default. This means:

- **Default voice** lives in Brix config (root, tablecloth, or Scribe module settings)
- **Per-prompt override** is a flag, recorded in the log's metadata
- **Voice change** is a config change, not a code change
- **Log extension** follows the voice: `*.kyri.md` when the voice is Kyri, `*.{other}.md` when it is another

The metadata for each log records the chosen voice name, so a reader looking at existing logs knows which voice produced them without needing to check the config that was active at the time.

### 100-char ratchet for session logs

Keaton asked for a TAME Guidance-aligned ratchet confining session log lines to **max 100 characters wide**. This is a tighter bound than the 120-char soft limit many style guides use, and it serves the same purpose TAME's bounds serve everywhere: name the budget at construction, enforce at the edge.

A 100-char line reads well on a phone screen in portrait, on a split editor pane, on a `git diff` in a terminal at 80 columns with the `+`/`-` prefix and some padding. It is a capacity a log line can fill honestly, and it is narrow enough that wrapping is visible the moment it happens.

The ratchet would be a new instrument in the `tame_style_check` family, reading `*.kyri.md` and reporting lines past 100 characters under a ceiling that only falls.

### Code block wrapping for raw data Markdown rendering

Keaton's insight: session logs wrapped in triple-backtick code blocks render their raw data as the **default Markdown view** on the web, rather than having Markdown interpret the fields as paragraph text. This means:

- A reader on GitHub sees the Kyri fields exactly as written -- no Markdown interpretation of `*`, `_`, `#`, or link syntax inside field values
- The raw data IS the display, rather than needing a special parser to see past Markdown rendering
- Links in the `file` field (which we already write as Markdown links for GitHub rendering) would move to a metadata section outside the code block, or the code block approach would be the outer wrapper with live links in a header section

The shape would be something like:

```markdown
---
format: session-log-v1
voice: kyri
stamp: 20261104.172718
---

` ` `kyri
stamp 20261104.172718
editor Claude Code
...fields...
` ` `
```

(Spacing added to avoid closing this document's own code blocks.)

This gives both: the YAML-style header for metadata tools, and the code-block body for faithful raw rendering.

### Molt breach over all existing logs

Keaton approved a **molt breach** editing all existing logs to fit the new scheme -- `*.{name}.md` extension, voice metadata, 100-char lines, code block wrapping. He acknowledged this is mechanical even though it touches thousands of files, and he is willing to standfast for it since it establishes the pattern for newcomers.

The scope, measured:

```
find session-logs/ -name '*.kyri.md' | wc -l    # .kyri.md logs (post-20261020 molt)
find session-logs/ -name '*.kyri' | wc -l        # elder .kyri logs (pre-20261020)
```

This is a substantial molt breach. The plan would be:

1. **Design the target format** -- the exact shape of the new `*.kyri.md` with voice metadata, code block wrapping, and 100-char lines
2. **Build the mechanical converter** -- a Rishi or shell script that reads each log, wraps the body in code blocks, rewrites long lines at natural breaks, adds voice metadata from the log's own `voice` field, and writes it back
3. **Run on a sample** -- prove the converter on ten logs from different eras, confirm they render correctly on GitHub
4. **Run the full molt** -- one commit, one signed send, with the converter's own witness proving the transform preserved every field value
5. **Lower the ratchet** -- seat the 100-char line instrument and the code-block format witness, both at zero from the start

This is a check-in (Claude) -- the exact format shape and the converter's behavior need a ruling before thousands of files move.

## Q4. Generation-based revocation -- explained

Keaton asked for more detail on this fork decision. Here is the explanation.

**The question:** grain-os uses **generation-based revocation** instead of seL4's **derivation tree**. Is this sound?

**What seL4 does:** seL4 maintains a tree of capability derivations -- when capability A is copied to make capability B, B becomes a child of A in the tree. To revoke A, seL4 walks the tree and destroys every descendant. This is thorough and well-proven, yet it costs memory (the tree is a data structure the kernel maintains) and time (revocation walks the tree).

**What grain-os does instead:** each kernel object has a 32-bit **generation counter**. Every capability to that object carries the generation it was minted at. When `CNode.revoke(slot)` is called:

1. The object's generation is bumped by one
2. The revoking slot's capability is updated to the new generation
3. **Every other capability anywhere in the system** that pointed to that object now holds a stale generation -- it is instantly invalid, without walking anything

This is **O(1) revocation** versus seL4's tree walk. The trade-off: there is no selective "revoke only this branch" -- revocation is all-or-nothing per object. grain-os answers that gap with **leases**: `Lease.arm(target, mask, duration, uses)` creates a forwarding capability that expires by time, use count, or explicit revocation. Lease resolution follows at most 4 hops, intersecting rights at each step.

**The open questions from grain-os's own CAPABILITY_MODEL.md:**

1. **Aliases the kernel does not track.** In seL4, if capability A is copied to slots B, C, D, the derivation tree knows about all of them. In grain-os, those copies all carry the same generation -- revoking any one revokes all of them, which is the intent. Yet the kernel does not know *how many copies exist* or *where they are*. The generation scheme's answer is: it does not need to, because bumping the generation invalidates them all at once regardless of location.

2. **Capabilities held by the kernel.** The kernel stores capabilities for threads (fault endpoints, bound signals). grain-os resolves these on every use -- `resolveCap` checks generation on each invocation -- so a lease cut off by time or use count takes effect even for kernel-held capabilities. This is sound as long as the resolution happens at use time rather than at storage time.

3. **Capabilities in flight in IPC.** A capability being transferred during an IPC call carries a generation. If the object is revoked between the send and the receive, the receiver gets a capability with a stale generation, which fails on first use. The gap is the window: the receiver might observe `invalid_cap` without knowing why.

**Verdict for our tree:** generation-based revocation is a strong, elegant simplification. For our rv32i target, where memory is precious and tree structures are expensive, this is especially attractive. The lease mechanism covers the selective-revocation cases. The open questions from CAPABILITY_MODEL.md Q1 are real engineering questions that grain-os acknowledges honestly, and each has a stated answer. The model checker and simulator prove Claims 1, 3, 4, and 5 exhaustively over small scenarios.

## Q5. Envoy protocol -- explained

Keaton asked for more detail. Here is the explanation.

**Envoy** is grain-os's interface between an AI agent and the running system. It is arguably grain-os's most novel contribution -- the place where "an AI operates an OS" becomes a concrete protocol rather than an aspiration.

**The six verbs:**

| Verb | What it does |
|---|---|
| **discover** | List the capabilities the agent holds, with their protocols and methods, described in plain English |
| **plan** | Propose a sequence of calls without executing them -- a dry run the owner can review |
| **apply** | Execute a planned sequence, or a single call |
| **undo** | Reverse a previous call (only for methods marked `undo=restore` in the protocol) |
| **ask** | Request a capability the agent does not have -- requires the owner's consent at the console |
| **observe** | Watch an event stream from a capability the agent holds |

**The security model:**

- The agent holds **only leases** -- never full capabilities. Leases carry `send` and `grant` rights, never `revoke`. They are bounded by time, use count, or both.
- **Askable capabilities** require the owner to say yes at the console. The agent can write to the console (it has a `console` grant), which means it could theoretically word output to mislead the owner into approving. grain-os's CAPABILITY_MODEL.md Q7 names this honestly as an open question. The mitigation: prompts start with `[owner]`, anything typed before the question appears is discarded, and the audit chain records everything.
- **Every call is audited** in a hash chain. The `log` command shows the chain; `hash chain: verified` means no entry has been tampered with.

**The MCP bridge:**

`tools/envoy.py mcp` exposes the same protocol as MCP tools, so Claude (or any MCP-capable agent) can operate a running Grain instance through the standard tool-use interface. The structured shell (`grainsh`) is the same protocol in a terminal.

**What this means for our tree:**

Envoy maps naturally onto what our foundations describe. Our Mantra module (the inference vane, now named Ember) is where agent-system interaction would live. The Envoy protocol is a concrete implementation of the pattern: typed interfaces, capability-bounded access, owner consent, audit chain. Studying it gives us a proven wire protocol to either adopt directly or use as a design input for Ember's own agent interface.

## Q6. Tablecloth crash model -- explained

Keaton asked for more detail.

**Tablecloth** is grain-os's content store -- the module that persists data across reboots. Its crash model is designed to survive a power cut at any instant without losing committed data.

**The invariant:** after a flush, the on-disk state is updated by a **single superblock write**. This means:

- Either the old superblock is on disk (the write did not complete), or
- The new superblock is on disk (the write completed)

There is no intermediate state where the store is corrupt. The superblock points to all the committed data, so the store is always recoverable from whichever superblock is on disk.

**The crash simulator:** `grain/lib/tablecloth.zig` includes a crash simulator in its test suite. The simulator:

1. Intercepts every write to the backing store
2. At every write boundary, forks the state: "what if power died right here?"
3. Verifies that the store is recoverable from the interrupted state

The `--kill-on` flag in qemu-test does the same thing at the system level -- it kills the QEMU process at a specified point and verifies the store recovers on reboot.

**Passphrase sealing:** private data is sealed under the owner's passphrase. The passphrase is typed at the console (`--console-input` in tests). The sealed data is opaque without the passphrase, so a stolen disk reveals nothing.

**What this means for our tree:**

Our Tablecloth module has the same name and the same mission -- a content store. grain-os's crash model gives us a proven pattern: single-superblock-write after flush, crash simulation in tests, passphrase sealing. These are design inputs for our own Tablecloth implementation. The crash simulator is especially valuable -- it is a testing discipline we can adopt directly, the same way we adopted TigerBeetle's disjoint-copy law.

## Q7. Glow as command language -- explained

Keaton asked for more detail.

**The question:** grain-os proposes a "command language" -- typed pipelines over capabilities. How does this relate to Glow?

**What grain-os describes:** the PLAN.md mentions a command language where typed values flow through pipelines of capability invocations. Instead of `cat file | grep pattern | wc -l` (untyped byte streams), you would write something like `store.list | filter(name="*.md") | count` where each stage is a typed capability invocation with checked protocols.

**Why Glow is a natural fit:**

Glow is already a typed functional language with a pipeline concept. It compiles to Nock (a minimal combinator calculus), and its rune syntax (`:-`, `:+`, `:/`) describes typed transformations. A Glow expression like:

```
:- store list
:+ filter name "*.md"
:+ count
```

...is exactly the shape grain-os's command language describes, yet it is also a valid program that type-checks, compiles, and runs. Glow's type system would catch a protocol mismatch at parse time rather than at run time.

**The composition:**

- **Glow** is the language -- its syntax, type system, and compiler
- **Rishi** is the shell -- the interactive surface where commands are typed
- **Capabilities** are the nouns -- each pipeline stage invokes a typed capability
- **Protocols** are the contracts -- each stage's input and output types are checked against the protocol

This means Glow is not just "our programming language" -- it is also the command language, the query language, and the composition language. One language, one type system, one compiler, many surfaces. This is the same economy grain-os is reaching for, and Glow already has the type infrastructure to deliver it.

## Q8. Kumara word bank -- explained

Keaton asked for more detail.

**Kumara** is grain-os's identity module. Its most distinctive feature is **three-word names** drawn from a word bank.

**How it works:**

Each Grain instance has an identity: an Ed25519 keypair. The public key is long and unreadable. Kumara maps it to a **three-word name** drawn from a curated word bank -- something like `bright-morning-river` (not the actual algorithm, just the shape). The name is human-readable, memorable, and unique enough for a small network.

**Ed25519 signing:**

Every action that matters -- an agent's call, a system upgrade, a peer introduction -- is signed with the instance's Ed25519 key. The key never leaves Kumara (grain-os's architecture ensures this -- the key is in a capability-protected domain).

**Domain-name-bound signatures:**

When a domain asks Kumara to sign something, the signature is bound to the **caller's domain name** as context. This means a signature asked for by the `store` domain cannot be passed off as one from the `console` domain. CAPABILITY_MODEL.md Q6 asks whether a name is a strong enough context, given that Steward assigns names from the manifest -- a fair question, since the manifest is the root of trust.

**Attestation protocol:**

Kumara serves attestations through a separate protocol (`attest.v1`). The context is `@attest`, which no domain name can be (names are `[a-z0-9_]`). Holding the attestation capability grants nothing else -- it is a read-only proof of identity.

**What this means for our tree:**

Our Kumara module has the same name. The three-word-name approach is warm and human, which fits our Comlink naming tendency. The domain-name-bound signature context is a clever pattern we should study -- it solves the "confused deputy" problem at the signature level. The Ed25519 choice aligns with our own identity direction (our tree already holds Monocypher at `vendor/monocypher` for signed-Kumara guest verify).

## Q11. Contribution standards -- recommendation and comparison

Keaton asked what I recommend, and to compare with our CONTRIBUTING.md, TigerBeetle's standards, and our foundations.

### Our CONTRIBUTING.md

Our contribution guidelines inherit Urbit's discipline:

- **Atomic, component-prefixed commits** under 50 characters
- **Gauge Style at Meter** -- exact, mechanism-first, refusal-aware
- **PR title classification** -- `[red]`, `[guard]`, `[foundations]`, `[rishi]`, etc.
- **Eight lanes** -- each with its own scope
- **GPG-signed** -- every commit, always
- **Kyri voice** -- commit messages are prose in our voice

### TigerBeetle's standards (from our alignment study)

Our tree already has a detailed TigerBeetle alignment study at `external-research/date/20260707/20260707-053212_tigerbeetle-alignment-study.md`. What we adopted from TigerBeetle:

- **Disjoint-copy law** -- `copy_disjoint` over bare `@memcpy`, walled at zero in authored code
- **Qualified assert ban** -- unqualified `assert` only, never `std.debug.assert(`
- **Compound assert split** -- no `assert(a and b)`, always two separate asserts
- **Error-compare ban** -- no `) == error.` or `) != error.` at call seams

What we ratchet from TigerBeetle:

- `@memcpy` application sites: 135 (migrating on touch)
- camelCase functions: ratcheting to `snake_case`
- Functions past 70 lines: splitting at natural seams

### grain-os's contribution standards

grain-os's CLAUDE.md is concise and practical:

- Toolchain pinned to Zig 0.17.0 exactly
- `zig build test && zig build qemu-test` before pushing
- New kernel behavior needs scenario test, invariant, and ktest
- Parsers of untrusted input need fuzz targets
- Design changes go into ARCHITECTURE.md in the same commit as code

### What I recommend

**Adopt grain-os's testing discipline as a design input.** Their requirement that every new kernel behavior needs three things -- a scenario test, an invariant check, and a user-facing test -- maps directly onto our witness discipline. Their fuzz-every-parser requirement maps onto our TAME Guidance's "bound everything" reflex.

**Keep our own standards.** Our CONTRIBUTING.md is already stronger in several areas:

- **Voice and style** -- Gauge at Meter gives commit messages a quality grain-os's do not reach for
- **Mechanism sentence** -- our commit-msg hook enforces plain engineering words in every body
- **GPG signing** -- grain-os does not mention commit signing
- **Lane structure** -- our eight lanes organize contribution by scope
- **Witness before narrative** -- our "a fix is closed by a witness on metal, never by a claim" is a standard grain-os's testing discipline approaches yet does not state as a law

**The alignment with radha prema bhakti and our foundations:** our contribution standards already embody what our foundations ask for. Gauge Style's first rule -- don't be too smart about it -- governs how contributions read. Bhakta Style governs onboarding pages. The Comlink tendency governs naming. Reds-first governs how errors are treated. These are not contribution standards in the narrow sense; they are a way of working that makes the work worth reading. grain-os's standards are practical and effective; ours are practical, effective, and beautiful. We keep ours and study theirs.
